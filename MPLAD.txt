ARCHITECTURE NAME
MPLADS Canonical Logic Architecture

REAL SCOPE
- Irreducible Coverage: Maintenance of constituency area scope and member entitlement-year position; structured work proposal authored exclusively by the Member; statutory scrutiny, technical feasibility verification, and work sanction by designated authority; execution state tracking; immutable geo-verifiable media evidence for completed assets; strict append-only action audit of all state changes; read-only AI decision-support for eligibility, duplication, cost-reasonableness, and need/gap analysis.
- Deliberate Non-Coverage: Individual benefits, predictive work-lists, auto-sanctions, multi-year spillover workflows, release/tranche management, physical file or document management, user interfaces, subjective public feedback, unstructured text remarks, and legacy data migration.

SYSTEM BOUNDARY
Logical architecture and logical database ONLY. Encompasses domain models, business rules, minimal business entities, minimal persistent business facts, minimal business processes, minimal AI augmentation, logical modules, integrity rules, authority separation, visibility rules, language-neutrality, identifiers, keys, relationships, and domain constraints. Excludes all physical implementations, UI/UX, frameworks, APIs, databases, hardware, storage, and presentation artifacts.

WORKFLOW
1. ENTITLEMENT-YEAR exists for (MEMBER,YEAR).
2. MP structures WORK-PROPOSAL with canonical minimal fields. Invokes Eligibility and Duplication AI support (read-only). Save if structurally valid.
3. Authority scrutinises: fund discipline, feasibility, Cost-Reasonableness AI support, area, eligibility, non-duplication. Either SANCTIONS → system-generated WORK, sets commitment/sanction, appends ACTION-AUDIT, state SANCTIONED; OR REJECTS → no WORK, appends ACTION-AUDIT with exactly ONE minimal reason.
4. SANCTIONED → IN-EXECUTION → COMPLETED (authorised) → UTILISED (authorised). Immutable WORK-EVIDENCE may append from SANCTIONED onward. Work-level expenditure/completion/utilisation updated only by authorised actions with audit.
5. All state changes audited. Public/officer visibility = read-only subset.

FUND FLOW
- Year-bound entitlement.
- Only WORK-level sanctioned amounts create commitments against ENTITLEMENT-YEAR.
- Derived balance: `balance = annualAmount − (sanctionedAmountSum of WORKs of that (MEMBER,YEAR) whose utilisation is NOT complete)`.
- No release/instalment flow. No multi-year spillover flow. No revision/re-appropriation flow.

AI SUPPORTS
1. ELIGIBILITY-SUPPORT: Computes {isCommunityPublicUtility, isDurableCommunityAsset, isIndividualBenefit}. If `isIndividualBenefit=true` → absolute disqualifier signal.
2. DUPLICATION-SUPPORT: Compares (language-independent public-utility + lowest required public locality) against PUBLIC-ASSET-INVENTORY and WORKs in {SANCTIONED, IN-EXECUTION, COMPLETED, COMPLETED-not-fully-UTILISED}. Returns {NO_DUP, POSSIBLE_DUP, LIKELY_DUP} and exactly ONE reason-token.
3. COST-REASONABLENESS-SUPPORT: Gross reasonableness band relative to minimal scope.
4. NEED/GAP-SUPPORT: Constituency-level public-utility presence/gaps from known assets and utilised/completed works.

SECTION C: MODEL 1 — ANOMALY DETECTOR
--------------------------------------------------------------------------------

C.1 Architecture
  Type: Ensemble (Random Forest + Gradient Boosting Machine, soft vote)
  RF Weight: 40% | GBM Weight: 60%
  Random Forest: 200 trees, max depth 9, min leaf 4
  Gradient Boosting: 150 estimators, max depth 5, learning rate 0.05,
                     subsample 0.8 per iteration
  Feature Scaling: StandardScaler (zero mean, unit variance)
  Oversampling: Proper SMOTE (k=5 nearest-neighbour interpolation)
  Post-SMOTE class balance: 2,280 Normal vs 2,280 Anomaly (1:1)

C.2 Training Performance
  5-Fold Cross-Validation Accuracy: 99.9% ± 0.1%
  F1 Score (Anomaly class): 1.000
  F1 Score (Normal class):  1.000
  Ensemble F1:              1.000

C.3 Input Features (30 features)

  RATIO FEATURES:
    expenditure_ratio       = actual_expenditure / approved_cost
    fund_utilization_ratio  = fund_released / approved_cost
    progress_gap_pct        = expected_progress_pct - reported_progress_pct
    progress_spend_gap      = reported_progress_pct - (expenditure_ratio × 100)
    delay_ratio             = delay_days / days_planned
    fund_leakage_ratio      = max(0, fund_released - actual_expenditure) / fund_released
    utilisation_eff         = actual_expenditure / approved_cost
    cost_overrun_flag       = 1 if actual_expenditure > fund_released, else 0

  TIME FEATURES:
    delay_days              = max(0, days_elapsed - days_planned)
    days_elapsed            = calendar days since project start
    days_planned            = originally planned duration in days

  PROGRESS FEATURES:
    reported_progress_pct   = progress declared by implementing agency (0–100)
    expected_progress_pct   = expected % completion given time elapsed (0–100)

  SITE/PUBLIC FEATURES:
    gps_distance_m          = distance in metres between evidence GPS and declared site
    citizen_reports         = number of public evidence uploads
    vendor_projects_count   = number of concurrent projects by same vendor
    ground_verification_flag= 1 if physical inspection done, 0 otherwise

  CATEGORICAL ENCODINGS:
    sector_enc              = label-encoded work category
    project_type_enc        = label-encoded project type (New/Repair/etc.)
    state_enc               = label-encoded state name
    state_cost_index        = state cost multiplier (from B.2)
    region_enc              = geographic region (South=0, West=1, North=2,
                              East=3, Central=4, NorthEast=5, Islands=6)

  ECONOMIC FEATURES:
    cpi_index               = India CPI for the project year (from B.1)
    gdp_growth              = India GDP growth rate for the project year

  INTERACTION TERMS (capture combined risk signals):
    delay_x_gps             = delay_days × gps_distance_m / 1000
    exp_over_x_citizen      = (expenditure>1.0 ? 1:0) × (1 - citizen_reports/10)
    leak_x_delay            = fund_leakage_ratio × min(delay_days/365, 2)
    state_x_delay           = state_cost_index × delay_days
    risk_x_exp              = risk_score × expenditure_ratio
    risk_score              = composite proxy:
                              min(delay/365,1)×30 + progress_gap/100×30
                              + min(gps/10000,1)×20 + (1-citizen/10)×10
                              + cost_overrun_flag×10

C.4 Prediction Output
  Returns probability P(anomaly) in [0,1] from ensemble.

  ALERT THRESHOLDS:
    P ≥ 0.70  → AI_ANOMALY_CRITICAL (🔴 CRITICAL)
    P ≥ 0.50  → AI_ANOMALY_HIGH     (🟠 HIGH)
    P ≥ 0.30  → AI_ANOMALY_MEDIUM   (🟡 MEDIUM)
    P < 0.30  → AI_ANOMALY_CLEAR    (ℹ️  INFO)

C.5 GBM Internal Mechanics
  Each iteration fits a regression tree to the residuals (actual_label −
  predicted_probability) using log-loss gradients. Softmax is applied across
  all classes after summing boosted scores. Learning rate 0.05 shrinks each
  tree's contribution to prevent overfitting.

SECTION D: MODEL 2 — COST REASONABLENESS
--------------------------------------------------------------------------------

D.1 Architecture
  Type: Non-parametric Quantile Band Model
  No single trained estimator — instead builds empirical percentile tables
  from 238,542 real MPLADS transactions.
  Three lookup levels (most-to-least specific):
    Level 1: sector × year   (45 bands)   — most precise, time-aware
    Level 2: sector × state  (298 bands)  — regional specificity
    Level 3: sector only     (13 bands)   — broadest fallback
    Level 4: state only      (36 bands)   — geographic fallback

  IQR Outlier Fence per sector:
    upper_fence = Q3 + 3.0 × IQR   (extreme statistical outlier threshold)
    lower_fence = Q1 - 3.0 × IQR

D.2 How a Cost is Evaluated

  Step 1: Normalise the project cost to 2023 base (see B.3 formula).

  Step 2: Look up the most specific available band for (sector, year, state).
          Fallback order: sector-year → sector-state → sector → default.

  Step 3: IQR extreme outlier check:
          IF normalised_cost > Q3 + 3×IQR
          → AI_COST_IQR_OUTLIER (🔴 CRITICAL)

  Step 4: Percentile band comparison:
          IF normalised_cost > P95  → COST_UNUSUALLY_HIGH   (🟠 HIGH)
          IF normalised_cost > P90  → COST_HIGH             (🟡 MEDIUM)
          IF normalised_cost < P5   → COST_SUSPICIOUSLY_LOW (🟡 MEDIUM)
          ELSE                      → COST_NORMAL           (ℹ️  INFO, shows percentile band)

  Step 5: Inflation context note:
          IF project_year < current_year - 1
          → Reports cumulative CPI inflation % since project year.
          Formula: inflation_pct = (CPI_current / CPI_project_year − 1) × 100

D.3 Sector Keyword Detection (for unstructured work descriptions)
  The system reads work description text and maps to canonical sectors:
    Road:        road, path, link, culvert, bridge, bypass
    Building:    building, hall, office, room, toilet, construct
    Water:       water, well, bore, tank, drain, canal, irrigation
    School:      school, education, library, classroom
    Health:      health, hospital, clinic, dispensary, ambulance
    Electricity: electric, solar, light, power, transformer
    Sanitation:  sanit, latrine, sewer, drain, waste
    Sports:      sport, ground, stadium, gym
    Repair:      repair, renovat, maintain, remodel, restoration
    Default:     Normal/Others

D.4 Band Statistics Stored Per Cell
  count, P5, P10, P25, median(P50), P75, P90, P95, P99, mean, std_dev
  All amounts are stored in 2023-normalised rupees.

SECTION I: ENSEMBLE VOTING FORMULA
--------------------------------------------------------------------------------

  For any binary or multiclass prediction:

  final_probability[class] = 0.40 × RF_probability[class]
                           + 0.60 × GBM_probability[class]

  Predicted class = argmax(final_probability)
  Confidence = max(final_probability)

  GBM Softmax (converts raw log-scores to probabilities):
    score[c] = log(prior_prob[c]) + Σ(lr × tree_output[c][t])
    probability[c] = exp(score[c]) / Σ exp(score[k])

  RF Aggregation:
    probability[c] = mean of leaf-node class-probability across all 180–200 trees

--------------------------------------------------------------------------------
SECTION J: SMOTE — HOW CLASS IMBALANCE IS HANDLED
--------------------------------------------------------------------------------

  Original labeled data: 2,280 Normal vs 220 Anomaly (10.3:1 imbalance)
  Without correction, a naive model would simply predict "Normal" always.

  SMOTE Algorithm (k=5 nearest neighbours):
    For each minority sample X_i:
      1. Find k=5 nearest neighbours in the minority class.
      2. Randomly pick one neighbour X_nn.
      3. Generate synthetic sample: X_new = X_i + α × (X_nn − X_i)
         where α ∈ [0,1] is random.
      4. This creates a point interpolated along the line between
         X_i and its neighbour — a realistic new anomaly, not just noise.
    Repeat until minority class size equals majority class.
  Post-SMOTE: 2,280 vs 2,280 (perfectly balanced).

SECTION O: DATABASE — HOW IT WORKS
--------------------------------------------------------------------------------

  Engine:   SQLite (a single file: mplad-app/prisma/dev.db)
  ORM:      Prisma — auto-generates a type-safe client from schema.prisma
  Location: mplad-app/prisma/dev.db

  The database contains 8 tables matching the logical architecture:
    1. Constituency        — stores constituency records
    2. Member              — stores MP (Member of Parliament) records
    3. EntitlementYear     — stores yearly fund entitlement per MP
    4. PublicAssetInventory— stores known durable community assets
    5. WorkProposal        — stores proposals submitted by MPs
    6. ImplementingAgency  — stores agencies that execute works
    7. Work                — stores sanctioned works (created only after sanction)
    8. WorkEvidence        — stores geo-tagged photo/video evidence (append-only)

  No separate database server is needed. SQLite is a file — it just works.

    First-time setup:
      npx prisma generate        ← Generates the Prisma client from schema
      npx prisma db push         ← Creates/updates tables in dev.db
    View database in browser:
      npx prisma studio          ← Opens a GUI at http://localhost:5555

SECTION V: RECENT TROUBLESHOOTING & FIXES (DETAILED LOG)
================================================================================

We encountered and fully resolved several issues while attempting to run the Next.js frontend application. Below is the exact step-by-step documentation of every single fix applied:

1. INCORRECT DIRECTORY EXECUTION
   - Error: Running `npm run dev` produced `npm error code ENOENT` and `Could not read package.json`.
   - Cause: The command was executed in the user's home directory (`C:\Users\nanth`) instead of the project directory.
   - Fix: Navigated to the correct project folder using `cd C:\Users\nanth\OneDrive\Desktop\MPLAD\mplad-app` before running the development server.

2. SCHEMA MISMATCH ON HOMEPAGE (app/page.js)
   - Error: The web application crashed with `Runtime TypeError: Cannot read properties of undefined (reading 'count')` at `db.workProposal.count()`.
   - Cause: The Next.js homepage (`app/page.js`) was referencing legacy database tables (like `WorkProposal`, `EntitlementYear`, `Constituency`, and `ImplementingAgency`) that no longer exist in the current `schema.prisma`. 
   - Fix: Completely rewrote the data fetching and metric aggregation logic in `app/page.js` (Lines 39-123). We switched the queries to use the current Prisma models: `Work`, `FundFlow`, `Mp`, and `Agency`. We also re-mapped the UI variables to use the newly available fields (e.g., mapping `w.state_term_id` to `w.status`, mapping `w.expended_amount` to `w.expenditure`).

3. SQLITE-PRISMA STRICT TYPING CONFLICT (constituency field)
   - Error: The dashboard crashed with `PrismaClientKnownRequestError: Error converting field "constituency" of expected non-nullable type "String", found incompatible value of "0"`.
   - Cause: SQLite is loosely typed, allowing integers to be stored in text columns. The `data/app.db` file had an integer `0` stored in the `constituency` column of the `mps` table. However, Prisma enforces strict types based on `schema.prisma` (which defines `constituency` as `String?`), causing it to crash when encountering an integer.
   - Fix: Executed a Python automation script in the background to connect to `data/app.db` via `sqlite3`. The script ran the query: 
     `UPDATE mps SET constituency = CAST(constituency AS TEXT) WHERE typeof(constituency) != 'text' AND constituency IS NOT NULL`
     This permanently fixed the integer mismatch and brought the database into 100% compliance with the Prisma schema.
